# PostgreSQL 인덱스 튜닝 — 측정 기반 의사결정 사례

> 뉴스 수집 대시보드 백엔드(witw)의 조회 성능을 개선한 과정 기록.
> 2026-09-14 작업. 인덱스를 넣기 전에 **채택/기각 기준을 먼저 정의**하고,
> 18회의 측정으로 후보를 걸러낸 뒤 최종 구성을 확정했다.

| 지표 | 값 |
|---|---|
| 전체 조회 성능 | 1485.2ms → **535.8ms** (2.77배) |
| 가장 느린 쿼리(C1) | 252.7ms → **12.4ms** (20.4배) |
| 측정 대상 | Repository 네이티브 쿼리 **21개 전부** |
| 측정 횟수 | 인덱스 구성 **18가지** |
| 채택 / 기각 | 인덱스 5개 채택, 2개 기각 |
| 쓰기 영향 | +19.9% (표본 17회 중앙값) |

---

## 1. 배경

### 서비스

전 세계 뉴스를 수집해 국가·테마·이슈별로 집계하고 논조(tone)를 보여주는 대시보드다.

- Kafka 컨슈머가 수집된 기사를 PostgreSQL에 **연속적으로 INSERT**
- 프론트엔드는 "최근 24시간" 기준 집계를 여러 화면에서 조회
- 테이블 구조: `field → theme → issue → article`, 그리고 기사-국가 언급 M:N 교차 테이블

**읽기와 쓰기가 동시에 일어나는 워크로드**라는 점이 이 작업의 핵심 제약이 된다.

### 발견한 문제

성능 측정 환경을 구축하고 처음 실행했을 때:

```
article 테이블 인덱스: pk_article (PK 하나뿐)
```

**`article` 테이블에 PK 외 인덱스가 하나도 없었다.** FK 컬럼(`theme_id`, `issue_id`,
`publisher_country_code`)조차 없었다. PostgreSQL은 외래 키에 인덱스를 자동 생성하지
않는데, 모든 대시보드 쿼리가 이 컬럼들로 필터하고 있었다.

50만 건 기준 베이스라인:

| 쿼리 | 실행 시간 | 스캔 | 버려진 행 |
|---|---|---|---|
| C1 `findThemesByField` | 252.7ms | Seq Scan | 337,005 / 500,000 (67%) |
| C8 `getCountryRankByArticleCounts` | 242.4ms | Seq Scan | — |
| C5 `findIncomingMentionRatios` | 114.4ms | Parallel Seq | — |

24시간 윈도우가 전체의 1/3만 남기는데, 인덱스가 없어 **50만 건을 전부 읽고 33만 건을
버리고 있었다.**

## 2. 접근 — 인덱스를 넣기 전에 판정 기준부터 정의

인덱스를 바로 추가하지 않고 **"무엇을 채택하고 무엇을 기각할지"를 먼저 문서화**했다.
기준이 없으면 "빨라진 것 같다"로 끝나고, 나중에 누구도 그 인덱스가 왜 있는지 설명하지
못하기 때문이다.

기준을 4개 층으로 분리했다. 한 덩어리로 만들면 서로 다른 성격의 판단이 뒤섞인다.

```
0층  테이블 예산     "이 테이블에 인덱스를 몇 개까지 허용하는가"  ← 쓰기 패턴이 결정
1층  서비스 목표     "이 화면은 몇 ms 안에 떠야 하는가"
2층  쿼리 합격선     "이 쿼리는 통과인가 불합격인가"
3층  후보 채택 규칙  "예산 안에서 어느 후보가 이기는가"
```

### 0층 — 테이블 예산

인덱스 비용은 **테이블 단위로 발생**한다. `article`에 인덱스를 하나 추가하면 그 인덱스를
어느 쿼리가 쓰는지와 무관하게 `article`로 들어오는 모든 INSERT가 느려진다.

그래서 "몇 개까지 허용할지"는 쿼리가 아니라 **그 테이블의 쓰기 패턴**이 정한다.

| 테이블 | 규모 | 쓰기 패턴 | 예산 |
|---|---|---|---|
| `article` | 계속 증가 | Kafka 컨슈머가 연속 INSERT | **5** |
| `article_country_mention` | article × 2~3행 | article 갱신마다 DELETE 후 INSERT로 **재작성** | **1** |
| `issue` | 200~ | ON CONFLICT upsert | 0 (PK+UK로 충분) |
| `country`(249) / `theme`(68) / `field`(5) | 작음 | 없음 | **판정 스킵** |
| `users` | 적음 | 가입 시에만 | 현행 유지 |

**스키마 9개 테이블 중 실제 작업 대상이 2개로 줄었다.** 이게 테이블 단위로 먼저 보는
가장 큰 효용이다.

작은 테이블(`field` 5행, `theme` 68행, `country` 249행)은 디스크 한두 페이지에 들어간다.
이 크기에서는 순차 스캔이 인덱스보다 빠르고 플래너도 인덱스를 무시한다. 조인에 계속
등장하므로 쿼리 단위로 보면 후보로 보이지만, **측정 대상에서 빼는 것이 정답**이다.

### 2층 — 쿼리 합격선

`EXPLAIN (ANALYZE, BUFFERS)` 출력에서 4개 지표만 본다.

| 지표 | 합격 | 불합격 | 이 지표가 가리키는 원인 |
|---|---|---|---|
| 실행 시간 | 화면 예산의 1/3 이하 | 초과 | — |
| 버려진 행 비율 | 50% 미만 | 90% 이상 | **인덱스 문제** |
| `Sort Method` | `quicksort Memory` | `external merge Disk` | **work_mem 설정 문제** |
| 추정 행 수 오차 | 10배 이내 | 100배 초과 | **통계 문제** (ANALYZE 부족) |

이렇게 나누면 "느리다"의 원인이 자동으로 갈린다. 설정 문제를 인덱스로 덮으려다 실패하는
일을 막는다. 실제로 베이스라인에서 이 지표들이 명확한 답을 줬다:

- 버려진 행 67~90% → ⚠️ 인덱스 문제
- 정렬은 전부 메모리 내 (최대 112kB) → ✅ work_mem 문제 아님
- 추정 163,556 vs 실제 162,995 (오차 0.3%) → ✅ 통계 건강

**"순수한 인덱스 문제"라는 결론을 근거를 갖고 내릴 수 있었다.**

### 3층 — 후보 채택 규칙

**추가 조건(전부 만족)**
1. 대상 쿼리가 실제 API 경로에 있을 것
2. 측정에서 **2배 이상** 개선 (1.3배는 노이즈와 구분 불가)
3. 개선 후 2층 합격선 통과
4. 쓰기 저하 **10% 이내**

**거부 조건(하나라도 해당)**
1. 기존 인덱스의 선행 컬럼과 중복
2. 0층 예산 초과
3. 신규 인덱스 합계가 힙의 30% 초과
4. `idx_scan = 0` (한 번도 안 쓰임)

## 3. 재현 가능한 측정 환경

성능 수치는 PostgreSQL 설정에 크게 좌우된다. 각자 로컬 설치본으로 재면 `shared_buffers`나
`random_page_cost`가 달라 숫자를 비교할 수 없다. 측정 전용 컨테이너에 설정을 고정했다.

```yaml
command: >
  postgres
  -c shared_buffers=256MB        # 일부러 테이블(307MB)보다 작게 — 디스크 I/O를 보기 위해
  -c work_mem=16MB
  -c random_page_cost=1.1        # SSD 기준. 기본값 4.0은 인덱스를 과도하게 불리하게 평가
  -c max_parallel_workers_per_gather=2   # 고정하지 않으면 머신마다 플랜이 달라짐
  -c track_io_timing=on
  -c shared_preload_libraries=pg_stat_statements
```

**데이터도 결정적으로 생성**했다. `random()` 대신 행 번호에서 해시로 유도해, 누가 언제
실행해도 바이트 단위로 동일한 50만 건이 나온다. 국가·테마 분포를 일부러 쏠리게 만들었다
(상위 1개국 29.5%, 상위 10개국 63%). 균등 분포면 모든 값의 선택도가 같아져서 플래너가
실제 운영에서 할 선택을 재현하지 못한다.

### 읽기만 재면 안 된다 — 쓰기 측정 도구 추가

Kafka 컨슈머가 `article`을 계속 INSERT하므로, 인덱스를 추가할 때마다 그 INSERT가
느려진다. 읽기만 보고 인덱스를 늘리면 **대시보드는 빨라지고 수집 파이프라인이 막힌다.**

1만 건 INSERT의 실행 시간을 재고 측정용 행을 정리하는 스크립트를 만들어, 모든 후보에
대해 읽기와 쓰기를 함께 측정했다.

## 4. 측정 과정에서 발견한 것들

여기가 이 작업의 실질적인 내용이다. 각 발견은 **측정하지 않았으면 틀렸을 판단**을
바로잡은 것이다.

### 발견 1 — 개별 측정만으로는 후보를 판단할 수 없다

후보 G1 `(publisher_country_code, published_at)`을 단독으로 측정하니 **심한 회귀**가
나왔다.

| 쿼리 | baseline | G1 단독 | 배수 |
|---|---|---|---|
| C11 | 35.1ms | 119.2ms | **0.29x** |
| D5 | 37.1ms | 103.5ms | **0.36x** |
| D4 | 36.2ms | 56.6ms | 0.64x |

`publisher_country_code`가 선행 컬럼이라 전체의 29.5%를 차지하는 국가 구간을 크게 훑기
때문이었다. 개별 판정이었다면 여기서 기각했을 것이다.

**그런데 다른 인덱스와 함께 놓으니 회귀가 전부 사라졌다.** 플래너에 더 나은 선택지가
생기기 때문이다. 조합에서 G1은 C7을 **12배** 개선하는 핵심 후보였고, G1을 빼면 C2가
baseline보다 느려졌다(0.72x).

> **교훈**: 인덱스는 단독으로 평가할 수 없다. 플래너는 사용 가능한 인덱스 전체를 보고
> 플랜을 고르므로, 후보 간 상호작용이 결과를 뒤집는다. 개별 측정은 "후보 발굴",
> 판정은 조합 측정으로 해야 한다.

### 발견 2 — 배치 측정은 캐시 워밍에 오염된다

22개 쿼리를 연속 실행하면 앞 쿼리가 뒤 쿼리의 캐시를 데운다. C1이 배치에서 147ms로
나와 "예산 150ms 통과"로 판단할 뻔했다.

같은 구성에서 C1만 단독으로 8회 재측정:

```
189.2  160.1  171.8  149.7  146.8  179.5  160.5  128.2   → 중앙값 160.3ms
```

**예산 미달이었다.** 배치 수치를 그대로 썼으면 잘못된 결론을 문서에 남겼을 것이다.

> **교훈**: 배치 측정치는 상대 비교용이다. 예산 근처에 있는 쿼리는 반드시 단독으로
> 다시 재야 한다.

### 발견 3 — 표본이 부족하면 결론이 뒤집힌다

쓰기 비용을 5회 측정했을 때 중앙값 기준 **+8.7%** — 10% 기준을 통과했다.

표본을 17회로 늘리자:

| 구성 | 중앙값 | 평균 | 저하 |
|---|---|---|---|
| baseline | 378.0ms | 377.9ms | — |
| 인덱스 5개 | 453.1ms | 465.7ms | **+19.9%** |

**기준을 명확히 초과했다.** 같은 구성에서 397~479ms로 흔들릴 만큼 분산이 커서, 5회로는
판정이 불가능했다.

> **교훈**: 쓰기 측정은 분산이 크다. 판정에 쓸 숫자라면 표본 수를 먼저 확인해야 한다.

### 발견 4 — 내가 세운 규칙을 내가 어기고 있었다

최초 추천은 인덱스 5개 전부(예산 만석)였다. 그런데 3층 조건 2번은 "2배 이상 개선"이다.
개별 후보의 baseline 대비 배수에만 적용하고, **조합 안에서의 한계 기여에는 적용하지
않았다.**

빠져 있던 조합을 추가 측정하니:

| 조합 | 합계 | 직전 대비 한계 기여 |
|---|---|---|
| G4+G5+G7 (3개) | 894.2ms | — |
| G1 추가 (4개) | 756.5ms | **1.18x** |
| G2 추가 (5개) | 735.9ms | **1.03x** ← 2배 기준 한참 미달 |

예산이 남았다는 이유로 기여도 3%짜리 후보를 넣고 있었다. 0층 문서에 "예산이 찼다고
억지로 채울 이유가 없다"고 써놓고 정작 5칸을 다 채운 것이다.

> **교훈**: 기준은 세우는 것보다 지키는 것이 어렵다. 후보 단위가 아니라 **한계 기여**로
> 평가해야 한다.

### 발견 5 — 인덱스보다 쿼리 구조가 먼저일 때가 있다

가장 느린 C1은 인덱스를 어떻게 조합해도 예산(150ms)을 맞추지 못했다(최선 160.3ms).
플랜을 보니 원인이 인덱스가 아니었다.

```
Bitmap Index Scan     8.9ms   ← 인덱스는 제 일을 하고 있음
Bitmap Heap Scan    134.8ms   ← 병목이 여기. 힙을 12만 행 방문
```

**인덱스 스캔은 빠른데 힙 접근이 느리면, 인덱스를 더 만들어도 해결되지 않는다.**

원본 쿼리와 재작성 쿼리의 플랜을 인덱스 0개 상태에서 비교했다.

```
원본 (320.5ms)
  HashAggregate                     rows=68          ← 여기서야 68행으로 줄어듦
  └ Hash Right Join    308.0ms      rows=122,900
    └ Hash Right Join  296.3ms      rows=122,900     ← 12만 행이 조인을 두 번 통과
      └ Seq Scan       284.0ms      loops=1          ← 단일 스레드

재작성 (86.3ms)
  └ Partial HashAggregate  78.8ms   rows=68  loops=3 ← 먼저 68행으로 줄임
    └ Parallel Seq Scan    75.3ms   loops=3          ← 워커 3개
```

문제가 세 겹이었다.

1. **집계를 조인 뒤로 미룸** — 최종 68행을 얻으려고 중간에 12만 행을 만들어 조인을 두 번 통과시킴
2. **병렬 실행이 막힘** — article 스캔이 LEFT JOIN 체인 안쪽에 갇혀 단일 스레드로 실행됨
3. **`COUNT(a.id)`가 Index Only Scan을 차단** — `a.id`를 가져오려고 힙을 방문해야 함

수정은 집계를 서브쿼리로 분리한 것뿐이다.

```sql
-- 원본: 조인 먼저, 집계 나중
SELECT f.id, f.name, t.id, t.name, COUNT(a.id)
FROM field f
LEFT JOIN theme t ON t.field_id = f.id
LEFT JOIN article a ON a.theme_id = t.id AND a.deleted_at IS NULL
                   AND a.published_at >= ... AND a.published_at < ...
GROUP BY f.id, f.name, t.id, t.name

-- 재작성: 집계 먼저, 조인 나중
WITH counts AS (
    SELECT a.theme_id, COUNT(*) AS article_count
    FROM article a
    WHERE a.deleted_at IS NULL
      AND a.published_at >= ... AND a.published_at < ...
    GROUP BY a.theme_id
)
SELECT f.id, f.name, t.id, t.name, COALESCE(c.article_count, 0)
FROM field f
LEFT JOIN theme t  ON t.field_id = f.id
LEFT JOIN counts c ON c.theme_id = t.id
```

효과 분해:

| 단계 | C1 | 해결한 문제 |
|---|---|---|
| 원본, 인덱스 0개 | 252.7ms | — |
| **재작성**, 인덱스 0개 | **87.2ms** | 문제 1 + 2 (**3.2배**) |
| 재작성 + 인덱스 | **12.4ms** | 문제 3 (**추가 7.4배**) |

**인덱스 없이 재작성만으로 3.2배**였고, 반대로 원본에 인덱스를 다 넣어도 160ms가
한계였다.

> **교훈**: 순서는 인덱스 먼저가 맞다(되돌리기 비용과 결과값 위험이 다르므로).
> 다만 플랜에서 "인덱스 스캔은 빠른데 힙 접근이 느린" 신호를 읽으면 그때가 쿼리
> 재작성 타이밍이다.

### 발견 6 — 쿼리 분류가 틀렸다

집계 쿼리 4개를 "인덱스로 해결 불가, 반정규화 대상"으로 분류했다. 측정해보니 3개가
인덱스로 해결됐다.

| 쿼리 | 세는 범위 | 인덱스 효과 | 실제 분류 |
|---|---|---|---|
| E1 `countByDeletedAtIsNull` | **테이블 전체** | 1.35x | 반정규화 대상 |
| E2 `findIssueById` | 이슈 1건 | **10.9x** | 인덱스로 해결 |
| E3 `getIssuePreviewByIssueId` | 이슈 1건 | **63.2x** | 인덱스로 해결 |
| E4 `getPrimaryIssuesByThemeId` | 테마 1건 | **50.0x** | 인덱스로 해결 |

판별 기준이 "LIMIT이 없다"가 아니라 **"WHERE로 범위가 좁혀지는가"**였다. E2~E4는
`WHERE i.id = ?`로 범위가 한정되므로 `issue_id` 선행 인덱스가 해당 행만 찾아낸다.
E1만 조건이 `deleted_at IS NULL`뿐이라 모든 행을 세야 한다.

> **교훈**: 분류는 가설이다. 측정으로 검증하지 않으면 불필요한 반정규화(= 동기화 책임)를
> 떠안게 된다. 스키마에 이미 사전 집계 테이블 2개가 설계돼 있었는데, 실제로 필요한
> 쿼리는 1개뿐이었다.

## 5. 최종 결과

### 채택한 인덱스 5개

전부 `WHERE deleted_at IS NULL` 부분 인덱스다. 모든 쿼리에 이 조건이 문자 그대로 있고,
soft delete가 약 2%라 인덱스에서 배제하면 크기와 선택도가 둘 다 좋아진다.

| 후보 | 인덱스 | 유형 | 근거 |
|---|---|---|---|
| G1 | `(publisher_country_code, published_at)` | 시간 윈도우 | C7 12배. 빠지면 C2가 baseline보다 느려짐 |
| G2 | `(published_at, theme_id)` | 시간 윈도우 | 재작성 C1에 7.4배 |
| G4 | `(theme_id, theme_relevance_score DESC, id ASC)` | **정렬 서빙** | D1 424배, D2 379배 |
| G5 | `(issue_id, issue_similarity DESC NULLS LAST, id ASC)` | **정렬 서빙** | E3 69배, E4 55배 |
| G7 | `(issue_id, published_at)` | 시간 윈도우 | E4 49배, C11 21배, D5 20배 |

**정렬 서빙 인덱스(G4, G5)가 압도적이었다.** 원래 후보 목록에 없다가 접근 패턴을 다시
분석하면서 추가한 것들이다.

```sql
WHERE a.theme_id = ? AND a.deleted_at IS NULL
ORDER BY a.theme_relevance_score DESC, a.id ASC
LIMIT 10
```

시간 조건 없이 정렬 후 LIMIT만 있는 쿼리는, 지금까지 테마에 속한 기사를 **전부 읽어
정렬한 뒤 10건만** 썼다. 인덱스가 정렬 순서를 그대로 제공하면 10건만 읽고 멈춘다.
`DESC`/`ASC`/`NULLS LAST`를 쿼리와 정확히 일치시켜야 `Sort` 노드가 사라진다.

### 기각한 후보 2개

## 6. 쿼리 재작성의 정합성 검증

성능 개선보다 **결과가 같다는 보장**이 어려운 작업이었다. LEFT JOIN 위의
`COUNT(a.id)`를 `COUNT(*)`로 바꾸면 **매칭되는 기사가 없는 테마가 0이 아니라 1로
세어진다.** 재작성에서 `COUNT(*)`가 안전한 이유는 서브쿼리 안이 LEFT JOIN이 아니라
단순 WHERE 필터이고, 바깥의 `COALESCE(c.article_count, 0)`이 0건 테마를 복원하기
때문이다.

원본과 재작성 결과를 `EXCEPT` 양방향으로 비교했다.

| 케이스 | 행 수 (원본/재작성) | 차집합 |
|---|---|---|
| 정상 (24시간, 모든 테마에 기사 있음) | 68 / 68 | 0 / 0 |
| **엣지** (1분 윈도우 + 기사 없는 테마 + 테마 없는 분야) | 70 / 70 | 0 / 0 |

정상 데이터만으로는 부족했다. 이 데이터셋은 모든 테마에 기사가 있어서 **핵심 엣지
케이스가 검증되지 않는다.** 시간 윈도우를 1분으로 좁히고 기사 없는 테마와 테마 없는
분야를 주입해서, 0건 테마 70개와 `theme_id IS NULL` 행 1개가 양쪽에 동일하게 나오는
것을 확인했다.

기존 단위 테스트도 이 두 케이스를 이미 검증하고 있었다.

```java
.containsExactly(tuple(940001L, 940001L, "Theme A", 2L),
                 tuple(940001L, 940002L, "Theme B", 0L),   // 기사 없는 테마
                 tuple(940002L, null,    null,     0L));   // 테마 없는 분야
```

전체 테스트 **87개 통과**(실패 0, 에러 0).

## 7. 남은 결정

쓰기 **+19.9%**가 3층 기준(10% 이내)을 초과한다. 자동 채택하지 않고 보류했다.

판단에 필요한 것은 **Kafka 컨슈머의 현재 처리량 여유**다. 운영에서 컨슈머 랙을 확인해야
알 수 있고, 여유가 있으면 조회 2.77배를 위해 기준을 완화하는 것이 합리적이다.
완화한다면 근거와 날짜를 문서에 남긴다.

여유가 없다면 G2를 빼고 4개로 가면 된다. **쿼리 재작성 덕분에 G2 없이도 C1이 91.5ms로
예산을 통과**하기 때문이다. 재작성의 부수 효과다.

측정으로 답할 수 없는 문제(운영 환경의 여유)와 측정으로 답한 문제(어느 인덱스가
효과적인가)를 구분해서, 전자는 결정권자에게 넘기고 후자는 근거와 함께 확정했다.

## 8. 이 작업에서 정리한 원칙

측정 과정에서 얻은 것들을 팀이 재사용할 수 있는 형태로 남겼다.

**인덱스 후보는 기계적으로 도출한다.** 쿼리에서 4가지만 추출하면 인덱스 모양이 거의
자동으로 나온다 — ① 등치 조건(선행 컬럼) ② 범위 조건(등치 다음) ③ 정렬(범위와 자리
경쟁) ④ 항상 참인 필터(부분 인덱스 WHERE 절). B-tree는 범위 조건을 만나는 순간 그 뒤
컬럼으로 탐색을 못 하므로 **등치 먼저, 범위 나중**이다.

**중복 인덱스는 순수 손해다.** 작업 중 실제로 정의가 동일한 인덱스가 두 개 만들어진
적이 있었다. 쓰기 비용은 2배로 물고 읽기 이득은 0이다. 복합 인덱스의 선행 컬럼과
겹치는 단독 인덱스도 마찬가지다.

**측정 스크립트는 코드 원문과 동기화한다.** 쿼리를 재작성한 뒤 측정 스크립트의 해당
섹션도 함께 갱신했다. 어긋나면 이후 측정이 전부 무의미해진다.

**실수를 막는 가드를 넣는다.** 데이터 생성 스크립트가 `TRUNCATE`로 시작하는데, 측정
중에 실제 데이터가 있는 로컬 DB에 연결된 채로 실행될 뻔했다. 스크립트 맨 앞에 연결
대상을 확인하고 아니면 중단하는 가드를 추가했다.

```sql
SELECT count(*) INTO foreign_rows FROM article WHERE id NOT LIKE 'perf-%';
IF foreign_rows > 0 THEN
    RAISE EXCEPTION 'perf 데이터가 아닌 기사가 %건 있습니다. TRUNCATE를 중단합니다.', foreign_rows;
END IF;
```

## 9. 면접에서 말할 포인트

**"인덱스를 어떻게 추가할지 정했나요?"**
→ 인덱스를 넣기 전에 채택/기각 기준을 먼저 문서화했습니다. 특히 테이블 단위 예산을
0층에 두었는데, 인덱스 비용은 쿼리가 아니라 테이블 단위로 발생하기 때문입니다. Kafka
컨슈머가 계속 INSERT하는 테이블이라 읽기 이득과 쓰기 비용을 같이 놓고 판단해야 했습니다.

**"측정에서 어려웠던 점은?"**
→ 세 번 속았습니다. ① 개별 측정에서 회귀가 난 후보가 조합에서는 최고 성능을 냈습니다.
② 배치로 잰 수치가 캐시 워밍에 오염돼 예산 통과로 잘못 판단할 뻔했습니다. ③ 쓰기
측정을 5회로 했을 때 +8.7%였는데 17회로 늘리니 +19.9%로 뒤집혔습니다. 전부 측정 방법
자체의 문제라, 결과를 믿기 전에 측정을 먼저 의심해야 한다는 걸 배웠습니다.

**"인덱스로 해결이 안 되는 경우는 어떻게 판단하나요?"**
→ 플랜에서 인덱스 스캔은 빠른데 힙 접근이 느리면(8.9ms vs 134.8ms) 인덱스를 더 만들어도
안 됩니다. 그 쿼리는 집계를 조인 뒤로 미뤄서 최종 68행을 얻으려고 중간에 12만 행을
만들고 있었고, article 스캔이 LEFT JOIN 체인에 갇혀 병렬 실행도 막혀 있었습니다.
집계를 서브쿼리로 분리하니 인덱스 없이도 3.2배, 인덱스와 함께 20.4배가 됐습니다.

**"쿼리를 바꿀 때 결과가 같다는 건 어떻게 보장했나요?"**
→ LEFT JOIN 위의 `COUNT(컬럼)`을 `COUNT(*)`로 바꾸면 매칭 없는 행이 0이 아니라 1로
세어집니다. `EXCEPT` 양방향 비교로 검증했는데, 정상 데이터만으로는 부족했습니다. 그
데이터셋은 모든 테마에 기사가 있어서 정작 위험한 케이스가 검증되지 않았거든요. 시간
윈도우를 1분으로 좁히고 기사 없는 테마를 주입해서 다시 확인했습니다.

**"결론을 못 낸 부분이 있나요?"**
→ 쓰기 +19.9%를 수용할지는 운영 환경의 컨슈머 처리량 여유를 봐야 알 수 있어서
보류했습니다. 측정으로 답할 수 있는 것과 없는 것을 구분해서, 전자는 근거와 함께
확정하고 후자는 판단에 필요한 정보를 명시해 넘겼습니다.
