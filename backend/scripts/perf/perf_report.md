# article 인덱스 후보 측정 결과

- 일자: 2026-09-14
- 환경: `docker-compose.perf.yml` 고정값 (shared_buffers 256MB, work_mem 16MB, random_page_cost 1.1, max_parallel_workers_per_gather 2)
- 데이터: `generate-bulk.sql` 기본값 — article 50만 건(힙 307MB), mention 113만 건(힙 56MB)
- 방법: 후보별 생성 → `ANALYZE` → `measure-table.sql` 2회(1회차 워밍, 2회차 채택) → 삭제
- 원본: perf DB `perf_run` 테이블 (`SELECT * FROM perf_summary`)

baseline C~E 합계 **1485.2ms** (F1·F2 제외, 20개 쿼리)

## 5. 한계 기여로 재검토 (초판 수정)

초판에서 `G1+G2+G4+G5+G7` 5개를 추천했으나, **3층 조건 2번(2배 이상 개선)을
개별 후보에만 적용하고 조합 안의 한계 기여에는 적용하지 않은 오류**였습니다.
예산 5칸을 채울 이유가 없는데 채웠습니다.

빠져 있던 조합을 추가로 측정했습니다.

| 조합 | 합계 | 직전 대비 한계 기여 |
|---|---|---|
| G4+G5+G7 (3개) | 894.2ms | — |
| **G1+G4+G5+G7 (4개)** | **756.5ms** | G1: 137.7ms (**1.18x**) |
| G1+G2+G4+G5+G7 (5개) | 735.9ms | G2: 20.6ms (**1.03x**) |

**G2 의 한계 기여는 2.7% 로 2배 기준에 한참 미달합니다.**

### C1 단독 재측정 (배치 수치는 캐시 워밍에 오염됨)

| 구성 | C1 단독 중앙값 |
|---|---|
| baseline | 252.7ms |
| 4개 (G1+G4+G5+G7) | 200.6ms |
| 5개 (+G2) | 160.3ms |

G2 는 C1 단독 기준으로는 1.25x 기여합니다(배치에서는 오히려 손해로 나왔음).
그래도 **어느 조합도 예산 150ms 를 못 맞춥니다.**

### G2 의 진짜 가치 — C1 재작성과 한 몸

| C1 구성 | 단독 중앙값 | 플랜 |
|---|---|---|
| 4개 + 원본 | 200.6ms | Bitmap Heap Scan (G7 오용) |
| 5개 + 원본 | 160.3ms | Bitmap Heap Scan |
| **4개 + 재작성** | **80.1ms** | **Seq Scan** (쓸 인덱스 없음) |
| **5개 + 재작성** | **12.3ms** | **Index Only Scan (G2)** |

재작성 쿼리가 `Index Only Scan` 을 타려면 `(published_at, theme_id)` 가 필요합니다.
**G2 가 없으면 재작성해도 Seq Scan 으로 떨어집니다.**

즉 G2 는 원본 쿼리에는 한계적(1.03x)이지만, 재작성과 함께라면 6.5x 입니다.
**G2 채택은 C1 재작성 결정에 종속됩니다.**

## 7. 결정이 필요한 사항

### ① 쓰기 +15% 를 받아들일 것인가

Kafka 컨슈머(`DbWriterService`)의 처리량 여유에 달렸습니다.
운영에서 컨슈머 랙을 확인해야 판단 가능합니다.

참고: `write-test.sql` 은 1만 건 대량 INSERT 라 Hibernate 의 건별 `saveAll` 과
형태가 다릅니다. 건별 경로는 왕복 비용 비중이 커서 실제 저하는 더 작을 수 있습니다.
또한 쓰기 측정은 분산이 커서(같은 구성에서 397~479ms) 표본을 10회 이상 잡아야 합니다.

### ② C1 재작성을 적용할 것인가

인덱스만으로는 어떤 조합도 예산(150ms)을 못 맞춥니다. 재작성하면 맞춥니다.

- 재작성만 (G2 없이): 80.1ms — 예산 통과
- 재작성 + G2: 12.3ms

재작성 방법과 정합성 검증(엣지 케이스 포함)은 `DOCS/PERF.md` 에 기록돼 있습니다.
적용 시 `FieldThemesRepositoryTest` 로 회귀를 확인하고,
0건 테마가 응답에 포함되는지 검증하는 케이스를 추가하십시오.

### ③ C5 (`findIncomingMentionRatios`)

G3 기각으로 개선 수단이 없습니다. 현재 105.8ms 로 국가 상세 예산(250ms) 안에는
들어오므로 당장 문제는 아닙니다. 데이터가 쌓이면 재검토하십시오.

## 8. C1 재작성 적용 후 재측정 (2026-09-14)

`ThemeRepository.findThemesByField` 를 재작성해 적용했습니다.
전체 테스트 87개 통과 (실패 0, 에러 0). `measure.sql` C1 섹션도 새 원문으로 갱신했습니다.

| 구성 | C~E 합계 | C1 |
|---|---|---|
| 원본, 인덱스 0개 | 1485.2ms | 252.7ms |
| **재작성**, 인덱스 0개 | 1265.3ms | **87.2ms** |
| 재작성 + 4개 (G1·G4·G5·G7) | 684.1ms | 91.5ms |
| **재작성 + 5개 (+G2)** | **535.8ms** | **12.4ms** |

### G2 판정이 뒤집힙니다

| 기준 | G2 한계 기여 |
|---|---|
| 원본 쿼리 | 756.5 → 735.9 = **1.03x** (기각 수준) |
| **재작성 쿼리** | 684.1 → 535.8 = **1.28x** (전체) / C1 91.5 → 12.4 = **7.4x** |

재작성 쿼리가 `(published_at, theme_id)` 로 Index Only Scan 을 타기 때문입니다.
대상 쿼리 기준 7.4x 로 3층 조건 2번(2배 이상)을 통과합니다. **G2 채택.**

### 최종 구성

`G1 + G2 + G4 + G5 + G7` (article 5칸) + C1 재작성

| 항목 | 값 | 기준 | 판정 |
|---|---|---|---|
| 읽기 개선 | 1485.2 → 535.8ms | 2배 이상 | ✅ **2.77x** |
| C1 | 252.7 → 12.4ms | 150ms 예산 | ✅ **20.4x** |
| 인덱스 크기 | 94MB / 307MB = 30.6% | 30% 이내 | 경계 |
| 예산 | article 5칸 | 5칸 | ✅ (여유 0) |
| **쓰기 저하** | **+19.9%** | 10% 이내 | ❌ |

### 남은 결정 — 쓰기 +19.9% 하나뿐입니다

C1 예산 문제는 재작성으로 해소됐습니다. 이제 판단할 것은 하나입니다.

Kafka 컨슈머(`DbWriterService`)의 처리량 여유를 운영에서 확인하십시오.
여유가 있으면 읽기 2.77x 를 위해 10% 규칙을 완화하는 것이 합리적입니다.
완화한다면 근거와 날짜를 `DOCS/PERF.md` 0층에 남기십시오.

여유가 없다면 4개 세트(G2 제외, 684.1ms)로 가고 C1 은 87~91ms 로 둡니다.
재작성 덕분에 G2 없이도 예산은 통과합니다.
